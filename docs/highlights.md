# 全栈开发面试实战指南：AI 知识库项目 (Enterprise RAG) 亮点总结

这份文档为你梳理了在这个 AI 知识库项目中涉及的**“企业级（Enterprise-grade）”工程亮点**。在面试时，面试官看不到你的源码，他们考察的是你的**架构视野、防范意识以及排查复杂系统问题的思路**。

建议采用 **STAR 原则**（Situation 情境 - Task 任务 - Action 行动 - Result 结果）来描述这些经验。

---

## 亮点一：接口安全治理与防御性编程 (Defensive Programming)

**面试官可能会问：** 
*   “你们后端的 API 是怎么做参数校验的？”
*   “除了把功能跑通，你在接口健壮性和安全性上做了哪些考虑？”

**核心叙述思路 (Parse, don't validate)：**
在设计 RAG 检索和文档管理接口时，我没有像传统做法那样在业务逻辑里堆砌大量的 `if-else` 类型判断，而是**全局引入了 Zod 声明式校验范式**。

*   **痛点：** 之前前端传过来的 JSON Payload（比如复杂的检索参数、对话历史数组、枚举类型的点赞/踩反馈）如果只用 TypeScript 的 `as` 进行断言，存在严重的“虚假安全”。一旦前端传来畸形数据（比如数组变成了对象，或者字符串类型的布尔值），直接透传给底层的大模型 SDK 或向量数据库，会导致引发服务端的 500 崩溃甚至引发注入风险。
*   **行动：** 我将所有暴露对外的 API（如 `/search`, `/ask`, `/feedback` 等）统一收口，在网关层使用 Zod Schema 进行强制约束。这样不仅做到了类型校验，还顺带完成了默认值填充（如默认的 TopK 和 Threshold）和脏数据清洗。
*   **结果与价值：** 遵循了现代后端 "Parse, don't validate" 的最佳实践。将非法请求（400 Bad Request）在进入核心业务逻辑前就全部拦截，极大地提升了服务端面对恶意或异常 Payload 时的稳定性，统一了全站的接口规范。

## 亮点二：服务端资源管理与 OOM 攻击防护

**面试官可能会问：** 
*   “你们怎么处理文件上传的？”
*   “有没有遇到过内存相关的性能问题？”

**核心叙述思路 (Early Return & Memory Management)：**
在实现知识库文档摄入（Upload）模块时，我重点重构了服务端的**内存加载顺序**，从而防范了潜在的 OOM（Out of Memory）崩溃和恶意内存消耗攻击。

*   **痛点：** 很多初级做法在处理 HTTP 流式表单上传时，会先使用 `arrayBuffer()` 将文件完整读入 Node.js 的 V8 内存（Buffer），然后再去判断文件后缀是否合法（比如是不是 PDF/TXT）。如果有恶意用户持续上传几个 GB 的视频文件，在触发格式校验之前，服务器内存就已经耗尽并宕机了。
*   **行动：** 我利用 HTTP 协议和表单解析时提前获取的元数据（File Metadata），实施了**前置的轻量级拦截**。我调整了执行顺序，先基于 `file.name` 和 `file.size` 进行严格的白名单校验和 10MB 大小限制。
*   **结果与价值：** 只有当请求完全符合业务条件时，才会真正触发 IO 操作将其读入内存进行向量化。这体现了我对服务端底层资源（IO与内存分配）的敬畏之心，从架构层面上杜绝了非法大文件造成的 DoS 攻击。

## 亮点三：跨层级“幽灵 Bug”排查与多租户架构隔离

**面试官可能会问：** 
*   “说一个你在项目中遇到的最难排查的 Bug。”
*   “在 Serverless 或者使用 BaaS（如 Supabase）时，你们是怎么做数据隔离的？”

**核心叙述思路 (Cross-layer Debugging & Multi-tenant Isolation)：**
这是一个非常精彩的排查数据库底层存储过程（RPC）残留逻辑的故事。

*   **情境 (Situation)：** 我们系统初期设计了多租户（Workspace）机制。后来为了敏捷迭代，应用层暂时弱化了这个概念，并且禁用了 Supabase 的 RLS（行级安全策略）。但在随后的测试中，我发现：新上传的文档能成功向量化并存入数据库，但大模型检索时却**始终显示 0 命中**。
*   **排查过程 (Action)：** 
    1.  我首先怀疑是向量生成算法的问题，但在排查了 Embedding API 和 Zod 校验流后，发现数据流转完全正常。
    2.  我将目光转向数据库层，通过审查执行日志，我发现底层用于余弦相似度计算的 RPC 存储过程（`match_documents`）代码并没有随着应用层的迭代而更新。
    3.  该存储过程中依然硬编码（Hard-coded）保留了对 `workspace_id` 的强过滤条件（`WHERE workspace_id = p_workspace_id`）。由于上传接口漏传了这个已废弃的概念字段，导致新插入的数据变成了缺少租户归属的“隐形数据”。
*   **解决方案与反思 (Result)：** 我通过在应用层热修复补齐上下文，使得读写两端重新对齐，解决了问题。这个坑让我深刻认识到：**在全栈架构中，数据库对象（Schema、存储过程）的生命周期必须与应用代码同频进行版本控制（Database Migration）**。应用层的重构如果忽略了底层数据库的硬逻辑，就会产生难以排查的跨架构断层。

## 亮点四：RAG 系统检索质量调优与降噪

**面试官可能会问：**
*   “你们的 RAG 系统准确率怎么样？遇到过幻觉吗？”
*   “如果检索出来的 Context 包含很多无关的垃圾信息，怎么处理？”

**核心叙述思路 (Chunking & Threshold Tuning)：**
在真实的文档测试中，我解决了 RAG 系统常见的**“过度召回（Over-fetching）”导致的上下文污染问题**。

*   **现象：** 在测试千字以上的企业管理手册时，如果问“入职带什么材料”，大模型虽然回答正确，但在 Reference 来源中，却把讲“试用期”和“着装规范”的段落也列了出来。
*   **分析：** 我深入到底层打分机制后发现，这是因为在业务语境下，文档片段都包含了“员工、公司”等高频词。这就导致无关段落的向量相似度也能达到 `0.4` 以上。由于系统最初设置的阈值（Threshold）偏低，且 `TopK` 允许召回多条，数据库就会把这些“刚好及格的噪音”全喂给大模型。
*   **调优手段 (Action)：**
    1.  **动态阈值调节：** 我在前端开发了 RAG 参数可视化控制台，通过对真实企业数据的反复评测，将阈值提高到了 0.55-0.6，瞬间将检索准确率（Precision）提升到了 95% 以上，彻底过滤了噪音 Chunk。
    2.  **分块策略升级认知：** 针对基础的定长切割（Fixed-size Chunking）容易破坏语义完整性的问题，我规划了向“基于 Markdown 标题结构（Heading-based）”和“语义段落”的拆分策略演进方案，确保每个被检索到的 Chunk 本身具备独立完整的逻辑。
    3.  **重排兜底：** 设计了在检索召回后，引入 Reranker 模型进行二次交叉打分的架构预案，用以弥补纯向量检索（Cosine Similarity）”只懂字面不懂逻辑”的缺陷。

## 亮点五：CRAG（Corrective RAG）with LangGraph 可视化

**面试官可能会问：**
- “你在这个 RAG 项目里用了什么方法提升检索准确率？”
- “LangGraph 和普通 LangChain Chain 的区别是什么？”
- “你的 AI Agent 是怎么处理检索结果质量差的问题的？”

**核心叙述思路（为什么 LangGraph，为什么 CRAG）：**

普通 RAG 把向量相似度当作唯一质量信号——相似度够高就直接喂给 LLM。但我在测试时发现，文档里如果大量出现”员工、公司”等高频词，不相关的段落相似度也能达到 0.5 以上，导致生成回答混入噪音上下文（幻觉来源）。

于是我引入了 CRAG（Corrective RAG）架构：

1. **问题：** 向量检索是”字面匹配”，无法判断语义相关性。
2. **行动：** 在 retrieve 之后加入 `gradeDocuments` 节点，用一次 LLM 调用批量评估所有 chunk 的相关性（relevant / partial / irrelevant），并给出结构化理由。
3. **关键设计：** 当无相关 chunk 时，不直接 fallback，而是触发 `rewriteQuery` 节点重写查询后重试——这形成了一个 `retrieve → grade → rewrite → retrieve` 的 cycle，这也是为什么选用 LangGraph 而不是普通 Chain 的原因：LangGraph 原生支持有环图，普通 DAG 框架无法表达这种重试逻辑。
4. **工程亮点：** graph state 与前端可观测事件严格分离——节点通过 `config.configurable.send` 回调推送事件，而不是把前端事件混进 graph state。这让 CRAG 的执行过程可以实时可视化（ReactFlow 实时节点动画），而不是黑盒。
5. **结果：** 检索准确率（Precision）提升，且每次执行都有 per-chunk 的评分记录，可追溯、可调试。

**LangGraph 使用理由（一句话）：**
> CRAG 的核心价值是在检索质量不足时重写查询重试，这个 retry cycle 是 LangGraph 的核心适用场景，普通顺序 Chain 无法表达有环图。
